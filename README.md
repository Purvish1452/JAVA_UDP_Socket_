# UDP Monitoring System

A Java 17 demonstration project that simulates a UDP server broadcasting packets to multiple concurrent UDP clients. The application registers clients, sends 10,000 packets to each client, and reports delivery and performance metrics.

## Project flow

```text
Main
 |
 +-- Starts UDPServer on port 9876
 +-- Starts a registration listener thread
 +-- Starts 5 UDPClient threads
 |     |
 |     +-- Each client sends REGISTER
 |     +-- Server records the client's IP address and UDP port
 |     +-- Server replies with REGISTERED_ACK
 |
 +-- Server broadcasts 10,000 packets to every registered client
 |     |
 |     +-- Clients deserialize packets and collect statistics
 |
 +-- Clients stop after 2 seconds with no new packet
 +-- Server and clients print their reports
```

With the default configuration, the server creates 10,000 logical packets and sends each one to five clients, for a total of 50,000 UDP datagrams.

## Project structure

```text
.
├── Main.java                     # Application entry point and flow coordinator
├── client
│   ├── UDPClient.java            # Registers, receives UDP packets, and reports results
│   └── ClientStatistics.java     # Calculates loss, delay, rate, duplicates, and ordering
├── model
│   └── Packet.java               # Data model transferred between server and client
├── server
│   ├── UDPServer.java            # Registration listener and packet broadcaster
│   └── ClientRegistry.java       # Thread-safe store of registered client endpoints
└── util
    ├── PacketUtil.java           # Binary packet serialization and deserialization
    └── ConsoleReport.java        # Formats server and client reports
```

## Classes

### `Main`

`Main` is the application launcher. It configures the default values, starts the server, creates five client threads, waits for client registration, initiates the broadcast, waits for receiving to finish, prints reports, and closes the server socket.

Default configuration:

| Constant | Value | Meaning |
|---|---:|---|
| `CLIENT_COUNT` | 5 | Number of concurrent clients |
| `SERVER_PORT` | 9876 | UDP port used by the server |
| `TOTAL_PACKETS` | 10,000 | Number of packets generated by the server |

### `UDPServer`

The server owns a `DatagramSocket` bound to port `9876`.

Its responsibilities are:

- receive client registration datagrams;
- store sender IP addresses and ports in `ClientRegistry`;
- acknowledge each successful registration with `REGISTERED_ACK`;
- generate, serialize, and send 10,000 packets to every registered client;
- measure total sends, bytes, elapsed send time, and throughput.

### `ClientRegistry`

UDP is connectionless, so the server does not automatically know its clients. `ClientRegistry` stores each registered endpoint as an IP address and UDP port.

It uses a thread-safe set. A client is unique when its address and port pair is unique.

### `UDPClient`

Every `UDPClient` runs in its own thread.

1. It opens a UDP socket on an operating-system-assigned temporary port.
2. It sends the text `REGISTER` to the server.
3. It waits up to three seconds for `REGISTERED_ACK`.
4. It receives binary packet datagrams and passes each packet to `ClientStatistics`.
5. It ends when no packet has arrived for two seconds, then closes its socket.

### `Packet`

`Packet` is the data object transferred over UDP. It holds:

| Field | Purpose |
|---|---|
| `packetId` | Unique ID for the generated packet |
| `sequenceNumber` | Expected order, normally 1 through 10,000 |
| `timestamp` | Server-side creation time in milliseconds |
| `payload` | Sample byte data |
| `payloadSize` | Payload length in bytes |

### `PacketUtil`

UDP can send only bytes, so `PacketUtil` converts `Packet` objects to byte arrays before sending and reconstructs them after receiving.

The binary wire format is:

```text
+----------------+--------------------+----------------+-------------------+------------------+
| packetId (8 B) | sequenceNumber (8 B) | timestamp (8 B) | payloadSize (4 B) | payload (variable) |
+----------------+--------------------+----------------+-------------------+------------------+
```

`serialize()` uses `DataOutputStream`; `deserialize()` uses `DataInputStream`.

### `ClientStatistics`

This class tracks the quality of delivery for one client:

- received packet count;
- unique packet count;
- lost packets;
- duplicate packets;
- out-of-order packets;
- bytes received;
- minimum, maximum, and average delay;
- receive rate in packets per second.

Formulas:

```text
Lost packets = expected packets - unique packets received
Delay        = client receive time - packet server timestamp
Receive rate = received packets / elapsed receive time
```

Duplicates are identified using a set of received sequence numbers. A unique packet is marked out of order when its sequence number is lower than the highest sequence number already received.

### `ConsoleReport`

`ConsoleReport` centralizes console formatting. It prints:

- Server report: generated packets, connected clients, sends, bytes, average packet size, send duration, and throughput.
- Client report: expected/received/lost packets, duplicates, out-of-order packets, delay values, bytes received, and receive rate.

## Registration protocol

```text
Client                                      Server
  |                                            |
  | ---- REGISTER ---------------------------> |
  |                                            | Store source IP and UDP port
  | <--- REGISTERED_ACK ---------------------- |
  |                                            |
```

The server sends packet data back to the same address and port from which each registration message arrived.

## Build and run

Requirements: Java 17 or newer.

From the project root:

```bash
javac Main.java client/*.java server/*.java model/*.java util/*.java
java Main
```

## UDP characteristics demonstrated

Unlike TCP, UDP does not guarantee delivery, ordering, duplicate prevention, or a connection handshake. This project handles the endpoint-discovery part through explicit registration and measures the rest through sequence numbers and timestamps.

When running locally (`127.0.0.1`), delay is usually very low. Sending many datagrams quickly can still cause loss if a receiving socket buffer cannot keep up.
